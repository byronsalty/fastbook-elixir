# Design docs & diagrams — authoring guide

This directory is the template for a project's `<DOCS_SRC>/_assets/` (default
`docs/design/_assets/`). Copy it in once (`/_standards-init` does), then author
Markdown and SVG in `<DOCS_SRC>/` and run `just docs-pdf`.

## What goes where

```
docs/design/                # DOCS_SRC — authoring dir, committed
  <topic>_design.md         # ONE document per topic, in parts (see below) — not a folder of docs
  <topic>_flow.svg          # the architecture diagram — committed (readers need no Python)
  _assets/
    docs.css                # print stylesheet (from this template)
    svgkit.py               # shared drawing helpers + palette (from this template)
    gen_<topic>_flow.py     # one generator per diagram; imports svgkit
publish/                    # DOCS_OUT — generated HTML/PDF; gitignored
```

## The Markdown

Pandoc GFM. Raw HTML passes through, so `docs.css` classes are usable directly:
`<p class="lede">…</p>` for the standfirst, `<div class="callout">` for a boxed
note (blank lines inside the div keep pandoc in markdown mode), `<p class="diagram-note">`
under an image. Embed a diagram with `![caption](name.svg)` — the build copies the SVG
beside the HTML and also emits `name-diagram.pdf` at full size, so say so under the
image ("Full size: publish/name-diagram.pdf"); a wide diagram is unreadable squeezed
into a body column.

**One document per topic, in parts** — not one file per concern. Readers want one
thing to open; the parts give it internal structure and each starts a new page in the
PDF (`h1` after the first). **Number the headings the standard way** — `# 1. Start
here`, `## 1.1 What this is about`, `### 5.2.1 Working set` — and cross-reference by
that number ("see 3.6"), never by a label that isn't printed on the page (a `§` or a
per-part letter code sends readers hunting). Ids for invariants and tests (W1, D4, H7)
are fine because they are printed in the lists and tables that define them. The
structure that has worked:

- **1. Start here**: what it is about, a reading order in three depths (five minutes /
  twenty / the full read), the decisions the design is waiting on (each with a
  recommendation; record the date when one is made), how it relates to the code as it
  stands.
- **2. Today**: how the code actually behaves, verified against it, with its own
  diagram; the pieces, the clocks (when each thing is written), one section per trigger
  in the SAME order as the flows in Part 4 (2.3…2.n ↔ 4.1…4.n), each ending with *Design
  changes*, and a "known gaps, verified" list. This is what makes the design reviewable
  as a diff, and what lets a later iteration see what moved.
- **3. The model**: vocabulary table · the picture · states / transitions / policy · a
  numbered invariant list (each becomes a test) · decisions, made and open · a phased
  path from here to there · "what the current code does that this changes".
- **4. Flows**: one walkthrough per trigger, ending with "what is lost if the process
  dies now".
- **5. Test catalog**: every invariant as a test at the cheapest layer that can
  express it, which existing tests carry over, fixtures worth building once.

## The diagrams

Hand-laid-out SVG, generated by a small Python script over `svgkit.py` so the
coordinates stay honest and the palette is shared. The idiom, in the order it appears
on the canvas:

1. **White canvas**, title (25px, 700) and a one-line thesis under it.
2. **Legend** — one swatch per *kind* of box. Kinds are the palette:
   `src` source/read-only (blue) · `und` in-memory state (violet) · `chg` change /
   decision (amber) · `doc` output (teal) · `per` a person acts (green) · `llm` an
   external call (rose) · `rec` record/database (slate) · `imm` immediate write (dashed
   orange) · `end` terminal / left alone (dashed grey). Text classes `tSrc`… match.
3. **Bands** — a tinted full-width rect per phase or layer, titled `A · NAME — one
   line`. Bands read top to bottom in the order things happen.
4. **Boxes** — `box` (centered text) or `lbox` (left-aligned lists); title in the kind's
   text color; identifiers, field names and code in `monosm` (pass `mono=(i,…)`).
   Keep a line under ~55 characters at width 300; widen the box before shrinking text.
   Diamonds for decisions with the question as the title and the rule as the subline.
5. **Arrows** — orthogonal polylines (`arrow([(x,y),…])`), grey by default; `flowG`
   green for a person's action, `flowR` rose for an external call's result, `flowA`
   amber dashed for an immediate write, `flowN` for a line with no head (buses,
   returns). Label with `lbl` only where the meaning isn't obvious.
6. **Footnotes** — three or four lines for the rules that don't fit in a box, plus a
   "Companion: …" line naming the docs.

Checklist before you call a diagram done:

- Render it and look: `rsvg-convert -w <W> name.svg -o /tmp/name.png`. Text
  overflowing a box, an arrow through a box, a label on top of a line, and black
  backgrounds (missing `begin()`) are all visible in one glance and invisible in the
  source.
- Every arrow enters and leaves a box edge, not its middle. Return arrows route
  around boxes on a dedicated x, never through them.
- SVG collapses runs of spaces — a "table" is separate `<text>` elements at column
  x offsets, not padded strings.
- Widen the canvas before shrinking type; 1400–1600 wide is fine, the standalone PDF
  is full size.

`gen_example.py` shows every helper in ~40 lines; copy it, rename, and edit.

## Requirements

Requirements no longer live under `docs/`. They are in the project's `spec/`
(`spec/requirements/`, numbered `PREFIX-NN`), with design decisions in
`spec/design/decisions.md` — see **Spec** in `PROJECT_STANDARDS.md`. A long-form
design doc here supports a How review for a large change; record the decisions
it settles as `DEC-NN` entries in the spec.

## Build

`just docs-pdf` → `bin/build-docs` (a symlink into `.standards/scripts/`). Set
`export DOCS_SRC := "…"` in the justfile if the docs aren't at `docs/design`.
Prereqs: `brew install pandoc librsvg` and Chrome. `publish/` is gitignored — the
PDFs are reproducible from the sources, so they never go in git.
